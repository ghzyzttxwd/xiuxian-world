## 0. 本任务书的权威级别

从本文件进入 `main` 起，后续开发以本任务书为**产品与工程的 Source of Truth（唯一任务基准）**。

执行规则：

1. 不再按聊天中临时想到的零散小功能随意推进；每次开发必须对应本任务书中的一个阶段、一个子任务或一项经明确批准后补入任务书的新任务。
2. **不得为了赶版本偷偷降低目标。** 如果一个阶段过大，可以拆成 A/B/C 子版本，但不能把“系统化”缩水成“加几件物品/加几个按钮”。
3. 每完成一个阶段，都要在本文件“进度总表”和“变更记录”中更新状态。
4. 若后续出现新的明确产品决策，与本任务书冲突时，应先更新本任务书，再改代码。
5. “代码写完”不等于“版本完成”。只有通过本任务书第 11 节的终验链，才能标记 `DONE`。

# 1. 项目总目标

V2.x 已经把世界、NPC、轮回、宗门、势力和高境界框架做出较多内容，但玩家自己的可收集、可培养、可搭配内容明显不足。

V3 系列的核心任务不是继续横向堆世界事件，而是完成一次**玩家成长体系纵向扩容**，最终达到：

- 功法不是几本固定倍率书，而是存在流派、适配、熟练、境界要求和取舍。
- 法术不是几个战斗按钮，而是形成完整的攻击、防御、身法、控制、神魂、持续伤害、保命等体系。
- 法宝不是“攻击 +95”的静态装备，而是有品质、炼制、祭炼、主动能力、被动词条、本命联系、损伤/修复和流派适配。
- 炼丹不是 4 个固定配方，而是形成材料 → 丹方 → 炼制 → 品质 → 丹毒/耐药 → 使用场景的循环。
- 地图、妖兽、秘境、宗门、坊市必须成为这些成长资源的真实来源，而不是彼此独立的页面。
- 四大道途必须能形成不同的长期玩法和战斗构筑。
- **模拟充值最后做。** 只有当正常游戏有足够多的资源、法宝、法术、丹药和培养线可以消费时，才允许开启充值/VIP/礼包开发。

最终目标不是“功能很多”，而是让玩家从凡人一路修至化神后期时，持续面对：

> 我要练什么、学什么、炼什么、装备什么、去哪找材料、要不要冒险、资源先给哪条成长线、这次突破值不值得赌。

# 2. V2.9 当前真实基线（2026-08-23）

以下为任务书创建时正式源码中的实际情况，用来判断 V3 的扩容幅度。

| 系统 | 当前规模 | 判断 |
|---|---:|---|
| 境界 | 26 档：凡人 → 化神后期 | 框架较完整 |
| 地图 | 12 区域 | 中等 |
| 路线 | 20 条 | 中等 |
| 功法 | 9 本 | 明显不足 |
| 法术/神通 | 11 个（包含基础拳脚） | 明显不足 |
| 道途 | 剑 / 火 / 体 / 神魂，共 4 条 | 有框架，内容不足 |
| 装备/法宝 | 7 件 | 严重不足 |
| 丹药/丹方 | 4 种 | 严重不足 |
| 真正法宝养成 | 基本没有 | 未成体系 |
| 炼器 | 固定材料 → 固定装备 | 很浅 |
| NPC / 轮回 | 求援、人情债、仇怨伤亡、动态势力、重大人生、前尘旧缘等 | 当前最深系统之一 |
| 模拟充值 / VIP / 商城 | 0 | 尚未开发 |

结论：

> V3 必须优先补“玩家自身成长纵深”，而不是继续把大量开发量投入 NPC 横向事件。

V2.8 / V2.9 已完成的 NPC、世界、转世和前尘旧缘能力必须全部保留，V3 只能在其上扩展，不能倒退。

# 3. 不可违反的固定约束

## 3.1 游戏与难度

- 玩家定位仍是**普通修士**，不增加“天道酬勤”“无脑倍率”“永久无敌”之类作弊核心。
- 境界越高，时间、资源、失败代价必须显著增加。
- 大境界差必须非常明显，不能靠低阶数值堆叠轻易跨大境击杀。
- 保留真实寿元、受伤、突破失败和死亡风险。
- 当前 V3 项目范围最高仍为**化神后期**；V3 系列完成前不开放炼虚。
- 模拟充值可以提供明显优势，尤其高 VIP，但不能把正常修仙系统变成纯数字跳过器。

## 3.2 模拟充值

- **绝不接真实支付。**
- 不接支付 SDK、不创建支付订单、不请求真实银行卡/微信/支付宝信息、不调用真实充值接口。
- 所有“人民币”“充值”“VIP”仅为单机游戏内部模拟数值。
- 模拟充值开发必须通过第 9 节的“充值前置门槛”后才能开始。

## 3.3 技术结构

以下结构继续固定：

- 正式运行链：`index.html -> app.js -> src/game-vXX.js`
- 浏览器直接读取源码。
- 禁止 `eval`。
- 禁止恢复历史 patch chain。
- 每个正式版本生成新的完整 `src/game-vXX.js`。
- `SAVE_KEY` 继续保持 `xiuxian_world_v02`。
- 每版提升 schema 时必须有旧存档迁移。
- 未来高 schema 存档必须拒绝被旧版本覆盖。
- V6 的 192/512 App 图标保持固定，不改图、不换 hash。

## 3.4 兼容性

- V2.9 schema26 存档必须能向 V3 正常迁移。
- 已拥有的旧装备、功法、法术不能因数据重构凭空丢失。
- 内容重构时必须使用稳定 ID；显示名称不能继续作为长期唯一主键。

# 4. V3 最终内容与深度门槛

以下是**最低门槛，不是“凑够数量就算完成”**。

在进入模拟充值开发前，正常游戏至少达到：

| 内容 | 最低目标 |
|---|---:|
| 功法 | ≥ 28 本 |
| 法术 / 神通 / 秘术 | ≥ 60 个 |
| 可收集装备与法宝 | ≥ 60 件 |
| 其中真正“法宝级”物品 | ≥ 24 件 |
| 丹方 / 可炼制丹药 | ≥ 20 种 |
| 明确命名的炼丹/炼器/突破材料 | ≥ 40 种 |
| 敌人与妖兽模板 | ≥ 45 种 |
| 有独特战斗机制的敌人 | ≥ 12 种 |
| 四大道途 | 每条至少 2 套真正可行的中高阶构筑 |
| 高阶资源获取渠道 | 秘境 / 野外 / 宗门 / 坊市或拍卖 / 炼制之间形成闭环 |

同时满足：

1. 每个主要境界段都有新的功法、法术、装备、丹药或材料目标，不能出现长时间“只有修为数字上涨”。
2. 每件中高阶法宝至少拥有一个区别于纯属性加成的机制。
3. 每条道途在战斗方式、资源需求、装备选择、核心技能上有真实差异。
4. 不允许 60 个法术实际上只是同一公式换名字和伤害数字。
5. 不允许 60 件装备只是攻击/防御数值等差数列。

# 5. 数据与内容架构改造原则

V3 内容量会远高于 V2，必须先解决“数据越多越难维护”的问题。

## 5.1 稳定 ID

逐步把内容改为稳定 ID：

- `manualId`
- `spellId`
- `itemId`
- `materialId`
- `recipeId`
- `dropTableId`
- `shopId`

显示名称只用于 UI，不再承担存档主键职责。

## 5.2 内容注册表

至少形成清晰的数据注册表概念：

- 功法定义
- 法术定义
- 装备/法宝定义
- 材料定义
- 丹方定义
- 掉落表
- 商店表
- 敌人技能表
- 后续模拟充值商品表

可以使用 `content/` 下的构建期数据文件或生成器片段维护，但**最终发布仍生成一份完整可读的 `src/game-vXX.js`**，不改变正式运行结构。

## 5.3 平衡字段标准化

所有成长内容尽量使用可统一检查的字段，例如：

- 品质
- 境界要求
- 道途/属性适配
- 灵力消耗
- 冷却
- 熟练度
- 主动效果
- 被动效果
- 获取来源
- 炼制成本
- 交易价值
- 是否可绑定/本命化

这样才能做自动回归和批量平衡检查，而不是到处写特殊判断。

## V3.0 — 玩家成长底座与数据化

**目标：先造能承载大量内容的骨架，不急着塞商城。**

### 任务

1. 稳定 ID 与 schema 迁移框架。
2. 旧功法、旧法术、旧装备从“名字即主键”向 ID 映射迁移。
3. 建立统一物品/材料注册表。
4. 建立统一掉落表结构。
5. 建立装备与法宝的品质体系。
6. 建立法术分类、冷却、熟练度等级、状态效果字段。
7. 建立玩家战斗 loadout：
   - 已学技能与“本场可用技能”分离；
   - 不再把所有学会的技能全部堆成按钮。
8. 建立炼器/炼丹统一配方数据结构。
9. 保证 V2.9 所有现有内容通过迁移后行为不丢失。

### 品质基础

装备/法宝至少按以下大类设计：

- 凡器
- 法器
- 灵器
- 法宝
- 古宝/特殊遗宝

大类内部可再有下品 / 中品 / 上品 / 极品，不要求每件都使用全部层级。

### 验收

- V2.9 存档自动迁移成功。
- 旧 9 功法 / 11 技能 / 7 装备 / 4 丹药仍可正常使用。
- 新注册表可通过脚本检查重复 ID、缺失引用、非法境界、非法掉落。
- 不改变玩家正常进度节奏，仅完成底层升级。

## V3.1 — 功法、法术、神通大扩容

**目标：让“学什么、练什么”真正成为构筑选择。**

### 功法体系

最终至少 28 本，分布到：

- 凡俗 / 炼气通用功法
- 筑基进阶功法
- 金丹功法
- 元婴功法
- 化神功法
- 青云剑道
- 赤霞火道
- 万兽炼体
- 太虚神道
- 宗门秘传
- 遗迹/奇遇功法

功法不再只有修炼倍率，至少可包含：

- 修炼效率
- 气血/灵力倾向
- 突破辅助或代价
- 对特定类型法术加成
- 对特定装备/法宝协同
- 特殊副作用或修炼条件
- 功法熟练度阶段

### 法术体系

最终至少 60 个技能，必须覆盖：

- 单体攻伐
- 群体/范围攻伐
- 持续伤害
- 护盾/减伤
- 身法/闪避
- 遁术/逃命
- 控制
- 封印/削弱
- 治疗/恢复
- 增益
- 神识/神魂攻击
- 反制/保命
- 四大道途专属技能
- 高境界神通

### 技能深度

每个技能至少考虑：

- 灵力成本
- 冷却或使用限制
- 熟练度成长
- 境界要求
- 功法/道途协同
- 法宝协同
- 特殊状态

禁止把所有技能做成“消耗灵力 → 造成不同数字伤害”。

### 战斗技能栏

- 玩家可以学会很多技能。
- 实际战斗设置有限的主动技能栏，建议 6 个主槽 + 少量被动/本命能力槽。
- 换装和换技能必须形成准备阶段，而不是战斗中无限切换。

### 验收

- 四大道途打法明显不同。
- 同一境界至少存在多个合理技能组合。
- 自动测试覆盖冷却、熟练、状态持续、技能切换和存档恢复。

## V3.2 — 法宝、装备与炼器体系

**目标：把“7 件固定装备”升级成真正修仙法宝养成。**

### 槽位结构

保留旧装备兼容，同时扩展为：

**基础装备**
- 武器
- 护甲
- 佩饰

**法宝能力**
- 攻伐法宝
- 护身法宝
- 辅助法宝
- 本命法宝（仅少量，作为长期核心成长线）

是否允许同一件物品同时占装备槽和法宝槽，由数据定义，不硬编码名称。

### 法宝机制

中高阶法宝至少从下列机制中拥有一项：

- 主动释放能力
- 被动触发
- 护盾
- 反击
- 吸收/转化伤害
- 提升某类法术
- 改变技能冷却
- 神魂防护
- 控制抗性
- 逃生/遁术
- 资源搜寻
- 炼丹/炼器辅助
- 突破辅助

### 炼器与养成

建立：

- 炼器配方
- 材料品质
- 炼制成功率或品质波动
- 祭炼层数
- 认主
- 本命化
- 法宝温养
- 大败/重创后可能出现“受损状态”
- 修复机制

不做每打一下掉 1 点耐久的琐碎系统；“损伤”只在重大失败、特殊敌技或高风险事件中出现。

### 本命法宝

- 不是普通装备换皮。
- 与角色长期绑定并随祭炼成长。
- 更换或毁损有明显代价。
- 与道途和核心功法有强协同。
- 高 VIP 未来可提供强力本命法宝相关资源，但本命体系本身必须先在正常游戏中完整成立。

### 内容量

到 V3.5 之前：

- 总装备/法宝 ≥ 60 件。
- 其中真正法宝级内容 ≥ 24 件。
- 至少 12 件拥有独立主动效果。
- 至少 12 件拥有构筑级被动效果。

### 验收

- 低中高境界都有合理换装目标。
- 不是所有玩家都无脑追同一把最高攻击武器。
- 剑、火、体、神魂都有自己的核心法宝组合。

## V3.3 — 炼丹、材料与资源循环

**目标：让地图上的每一种危险都能对应具体的成长资源。**

### 材料体系

至少覆盖：

- 普通灵草
- 属性灵草
- 妖兽皮骨/血肉/妖丹类
- 矿石/灵金
- 火行材料
- 水行材料
- 阴魂/神识材料
- 古修残物
- 高阶灵材
- 突破专材
- 炼丹辅材
- 炼器辅材

最终明确命名材料 ≥ 40 种。

### 丹药体系

最终可炼丹药 ≥ 20 种，至少覆盖：

- 治伤
- 回灵
- 临时增益
- 修炼辅助
- 筑基/金丹/元婴/化神阶段辅助
- 神魂恢复
- 解毒/解除异常
- 炼体类
- 高风险爆发类

### 炼丹深度

加入：

- 丹方获取
- 炼丹熟练度
- 成丹品质
- 成功率
- 炉毁/失败损失控制
- 丹毒或同类丹药短期耐受机制

目的：防止玩家无脑连吃几十颗同种丹药直接冲境界。

### 资源获取闭环

每个主要区域至少拥有独特材料或掉落倾向。

例如：

- 赤霞谷：火行炼器/炼丹材料
- 落星矿脉：矿石与灵金
- 万兽山脉：兽材与高阶妖兽材料
- 古河遗迹：古修残物与特殊丹方/法宝图谱
- 玄阴禁地：阴魂、神识、化神相关材料

### 验收

- 玩家为了目标法宝/丹药会主动选择地点，而不是任何地图都刷同一种“兽材”。
- 资源来源可以追溯，在 UI 中能看到“去哪找”。

## V3.4 — 战斗、敌人和四大道途构筑闭环

**目标：让前面扩充的技能和法宝真正改变战斗。**

### 战斗基础

统一处理：

- 近身/武器伤害
- 法术伤害
- 神魂伤害
- 防御/护盾
- 控制与抗性
- 持续伤害
- 增益/减益
- 冷却
- 逃跑与身法
- 大境界压制

### 四大道途

#### 青云剑道

- 高爆发
- 剑类法宝强协同
- 连击/御剑/剑意
- 防护相对依赖剑阵、护身法宝

#### 赤霞火道

- 高法术输出
- 持续灼烧
- 范围能力
- 自身防护偏弱或存在过热/反噬代价

#### 万兽炼体

- 高气血、高正面承伤
- 肉身技、反击、重击
- 灵力依赖较低
- 法术通用性较差

#### 太虚神道

- 神魂、控制、封印
- 灵力与神识优势
- 对部分敌人极强，但遇到高神魂抗性目标不能无脑碾压

### 敌人

最终敌人模板 ≥ 45 种，其中至少 12 种有独立机制，如：

- 护盾
- 狂暴
- 中毒
- 灼烧
- 神魂冲击
- 禁疗
- 破法宝
- 召唤
- 逃跑
- 控制抗性
- 阶段转换

### 验收

- 四大道途至少各有 2 套中高阶可行构筑。
- 对同一个敌人，不同构筑应有不同处理方式。
- 高境界不能只靠 HP 和攻击倍增来体现难度。

## V3.5 — 正常游戏完整化、经济与总平衡

**目标：在完全没有模拟充值的情况下，把普通游戏先做成一个闭环。**

### 经济渠道

至少形成：

- 普通坊市
- 宗门兑换
- 特殊商人/黑市或遗迹交易
- 高阶拍卖/稀有交易渠道
- 掉落、任务、炼制之间的价格关系

### 世界整合

已有 NPC / 宗门 / 势力系统要与新成长体系连接：

- NPC 求援可能需要具体丹药/材料。
- 宗门贡献可换专属功法、丹方、法器。
- 势力冲突影响部分资源和商路。
- 秘境掉落独特法宝图谱、丹方、材料。
- 前尘旧缘奖励保持“小而有意义”，不能变成跨世复制高阶法宝的漏洞。

### 正常玩家通关式测试

必须测试至少：

1. 新存档从凡人起步。
2. 不使用任何模拟充值。
3. 能通过正常玩法获得功法、技能、材料、法宝、丹药。
4. 能走至少四种不同路线中的任意一种进入高境界。
5. 金丹、元婴、化神资源压力逐级明显上升。
6. 高境界失败依旧有实质代价。
7. 多世轮回不出现旧人情债、旧礼包、旧付费状态等错误继承。

# 8. V3.6 — 深度模拟充值、VIP 与商城

**目标：做成“真正手游式”的单机内部模拟，而不是一个 +1000 灵石按钮。**

## 8.1 基础钱包模型

至少分开：

1. **模拟充值额度**：表示今天允许模拟充值多少“人民币”。
2. **累计充值金额**：只增不减，用于 VIP 和累计充值活动。
3. **高级货币**：模拟充值后获得，例如仙玉；商城消费扣仙玉，不直接扣“人民币”。
4. **绑定/赠送货币（可选）**：活动赠送，与充值货币区分。
5. **消费记录**。
6. **充值记录**。
7. **礼包领取记录**。

## 8.2 已固定的模拟充值规则

- 第一个真实日历日：模拟充值上限 **¥10,000**。
- 之后每个真实日历日：模拟充值上限 **¥3,000 / 日**。
- 日限额按设备本地日历日计算，**不能按游戏内“修炼一天”计算**，否则玩家可通过推进游戏天数无限刷新额度。
- 这是单机模拟，不做服务器级防改时间安全，但存档逻辑必须正确处理跨日。

## 8.3 VIP

- VIP 从 V0 往上分级。
- **V8 约对应累计模拟充值 ¥10,000**，这是当前固定方向。
- V8 必须有“明显强、值得感知”的奖励与特权，不能只是每日多领 5 灵石。
- 具体 V1～V10 阈值、奖励数值在 V3.5 总平衡完成后再定，避免现在拍脑袋定经济。

VIP 奖励可以包含：

- 培养效率
- 每日资源
- 商店刷新/折扣
- 炼丹炼器便利
- 法宝祭炼资源
- 特殊外观/称号
- 强力但有边界的本命法宝相关奖励
- 高等级 VIP 专属礼包

原则：高 VIP 可以明显舒服、明显强，但不能把寿元、死亡、境界、材料、战斗等整个游戏全部变成一键跳过。

## 8.4 商城与活动模块

至少实现：

- 首充
- 累计充值
- 每日充值
- VIP 礼包
- VIP 商店
- 每日/每周资源礼包
- 境界突破礼包
- 法宝培养礼包
- 丹药/炼器礼包
- 月卡模拟
- 成长基金模拟
- 限时礼包
- 累计消费活动

## 8.5 智能触发礼包

模拟手游常见触发，但不弹到干扰游戏：

- 第一次筑基
- 第一次金丹
- 第一次元婴
- 第一次化神
- 第一次本命法宝
- 大境界突破失败
- 重伤/死亡后
- 缺少某种关键突破资源时

触发礼包必须有冷却和次数限制，不能每次点击都刷屏。

## 8.6 充值模拟安全与一致性测试

必须验证：

- 刷新页面不能重复首充。
- 回档/迁移不能重复领取累计充值奖励。
- 同一天额度不能异常重置。
- 跨日额度正确刷新。
- VIP 经验与累计充值一致。
- 购买失败不能扣货币。
- 扣货币后必须有完整物品交付。
- 多世轮回默认继承“账号级付费状态”，但不能错误继承属于某一肉身/本命物品的状态；具体继承边界需要显式定义。

# 11. 每个版本的工程完成标准

所有 V3 版本继续执行严格发布链。

## 11.1 开发阶段

- 从当前正式 main 读取真实代码。
- 只实现本版本边界内任务。
- 构建生成完整新版本源码。
- Node 语法检查。
- 版本专项回归。
- 旧版关键回归。
- schema 迁移测试。
- 固定 V6 图标 hash 校验。

## 11.2 临时验证 PR

- 从正式 main 创建验证 branch。
- CI 必须在 PR branch 上先跑。
- 失败先在 branch 修复。
- PR 全绿后关闭，**不合并**。
- 正式 main 只接收已验证的精确文件。

## 11.3 正式发布

- main 正式 trigger。
- 生成 runtime commit。
- 精确发布到 gh-pages。
- 从真实 GitHub Pages 重新下载：
  - `index.html`
  - `app.js`
  - 当前 `game-vXX.js`
  - `sw.js`
  - `manifest.webmanifest`
  - 固定图标
- 验证版本标记。
- 验证当前 game SHA 与 build report 一致。
- 运行 public headless regression。
- 验证 manifest。
- 验证固定图标 hash。
- 写入该版本 `PUBLIC_VXX_STATUS.json = PASS`。
- 再从真实 Pages 重新读取 PASS 文件确认其可访问。
- 同样 PASS 回写 main。
- 比较“已验证 runtime 基线 → final main”，只允许预期状态文件发生额外变化。

只有完成以上步骤，才能对外说：

> **“Vx.x 正式完成。”**

# 15. 明确禁止的“伪完成”方式

以下情况不能算完成：

- “法宝系统完成” = 只多加 10 件攻击/防御装备。
- “法术扩容完成” = 同一伤害函数复制 30 次换名字。
- “炼丹完成” = 只多几个材料数字和按钮。
- “商城完成” = 一个充值按钮直接加灵石。
- “VIP 完成” = 只有 V1～V10 标签，没有真实权益。
- “发布完成” = GitHub 代码存在，但 Pages 没有重新验证。
- “测试完成” = 只有语法检查，没有玩法回归。
